# Catch the user up

Use when the user asks what changed or needs to catch up after a long run. Anchor the delta to their last substantive message before the catch-up request, or to the period they named. Agent notifications and tool results do not move that boundary. Include any earlier human decision still pending.

Keep the catch-up read-only. Inspect the current state of work touched by this task when useful; distinguish a fresh observation from an older report or unavailable state. Do not change code, start an app or job, create visuals requiring new execution, or post messages to produce a status reply. Reuse existing screenshots, recordings, and evidence. A small diagram can explain known relationships; never invent a screen or result.

Lead with the most consequential change and whether anything needs the user. Explain outcomes and their implications in plain language. Distinguish finished, running, failed, and unverified work. Include only decisions or access the user must supply as action items, with a recommendation and material consequence of waiting. Work the agent can still perform within scope belongs with remaining work. Do not invent a decision to fill the report. List every item still waiting on the user, including each item within a grouped decision. Give enough context to decide from the reply: consequence, recommendation, supporting evidence, and material risk or uncertainty. Links supplement that context. Mark unavailable facts unknown; never omit waiting items merely to meet a length target.

Use as little text as the delta needs. Link supporting detail and show existing visual evidence when it materially helps; avoid repeating the same facts in text and visuals. A catch-up request during active work does not cancel that work: answer briefly, then resume work already authorized unless the user asks to pause or stop.
